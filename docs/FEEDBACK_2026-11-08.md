## 3. Confusing behaviour

- **Staff lists are paged.** Accounts, profiles and categories show 20 rows per page with page numbers and "Go to Page", like the customer list. Searches keep their filters across pages.
- **No "Page X of Y" text (9 November).** Every list's pager now shows only the page numbers and "Go to Page". The highlighted number is the current page and the last number is the last page, so the extra line repeated them. The new check failed first (`page-of-red.xml`), then passed; screenshot `13-pager-without-page-of.png`.
- **Row buttons stay on one line.** View / Edit / Suspend no longer wrap.
- **Public header.** "Interior designers" became **For Designers** and opens the designer login. The duplicate top-bar "Log In / Sign Up" and "For Interior Designers" links are gone. Staff login pages no longer show Sign Up.
- **Page names** (chosen on 8 November):

  | Page | Menu | Heading |
  |---|---|---|
  | Designer home | Home | Interior Designer Home |
  | Customer project list | Browse Projects | Interior Design Projects |
  | Designer project list | My Projects | My Interior Design Projects |
  | Platform Manager categories | Categories | Project Categories |
  | Designer statistics | Statistics | Portfolio Statistics on all four tabs |

- **Edit button.** Categories use "Edit" like the other lists; the edit page heading stays "Update Category".
- **Labels.** "Email" for login email (the company form keeps "Contact Email") and "Full Name" on both sign-up pages. Login headings name the role: "Customer Log In", "Interior Designer Log In", "User Admin Log In", "Platform Manager Log In".
- **Saving wording** stays per role, as in the user stories: Favourites (Customer), Shortlists (Designer) and New Saves (report).
- **Dates** read "9 Jun 2026" or "9 Jun 2026, 1:59 PM" instead of raw database text.
- **Plurals.** "1 account" and "2 accounts" replace "account(s)" everywhere.
- **Browser tab** for an account shows the person's name.
- **Restart keeps people logged in.** The secret key is saved in `.renofolio_secret_key` next to the database (excluded from Git). On Render, the `SECRET_KEY` setting is used instead.
- **Fonts are local.** Inter and Fraunces are served from `app/static/fonts` (SIL Open Font License), so an offline demo looks the same.
- **First page photos.** The three preview tiles always show different photos.
- **Photo after a form error.** If a project form has an error, the uploaded photo is discarded and the message asks to choose it again, instead of showing a preview that would not be saved. This one was found while fixing bug 5.

### Draft US60 Reactivate User Account

**User story:** As a User Admin, I want to reactivate a suspended user account, so that the user can log in again after a mistaken or finished suspension.

| Use case | UC60 Reactivate User Account (US60) |
|---|---|
| Actor | User Admin |
| Preconditions | The User Admin is logged in (US09) and is viewing a suspended account (US43). |
| Normal flow | 1. The User Admin clicks Reactivate. 2. The system asks to confirm, saying the user will be able to log in again. 3. The User Admin clicks Reactivate to confirm. 4. The system checks the request. 5. The system identifies the User Admin from the session. 6. The system sets the account's status to Active. 7. The system shows "Account reactivated." |
| Postconditions | The account is active and can log in, provided its profile is active. |
| Alternative flows | A1. Cancel (step 3): nothing changes. A2. Already active (step 6): "This account is already active." A3. Profile still suspended (step 7): the message adds "Their … profile is still suspended, so they cannot log in until the profile is reactivated." A4. Account not found: "This account no longer exists." A5. Session expired (step 5): the login page (US09). |
| Code | `ReactivateUserAccountDialog` → `ReactivateUserAccountController.execute()` → `UserAccounts.reactivate()` |
| Tasks | T1 design (1.5 h), T2 tests first (1 h), T3 entity `UserAccounts.reactivate()` (1 h), T4 controller (1 h), T5 dialog, button and route (1.5 h), T6 integration (1 h) |

### Draft US61 Reactivate User Profile

**User story:** As a User Admin, I want to reactivate a suspended user profile, so that its accounts can log in again.

| Use case | UC61 Reactivate User Profile (US61) |
|---|---|
| Actor | User Admin |
| Preconditions | The User Admin is logged in (US09) and is viewing a suspended profile (US48). |
| Normal flow | 1. The User Admin clicks Reactivate. 2. The system asks to confirm, saying active accounts with the profile will be able to log in again. 3. The User Admin confirms. 4. The system checks the request. 5. The system identifies the User Admin from the session. 6. The system sets the profile's status to Active. 7. The system shows "Profile reactivated." |
| Postconditions | The profile is active; its active accounts can log in again. |
| Alternative flows | A1. Cancel (step 3): nothing changes. A2. Already active (step 6): "This profile is already active." A3. Profile not found: "This profile no longer exists." A4. Session expired (step 5): the login page (US09). |
| Code | `ReactivateUserProfileDialog` → `ReactivateUserProfileController.execute()` → `UserProfiles.reactivate()` |
| Tasks | Same as US60 with the profile classes. |
